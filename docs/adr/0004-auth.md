# 0004. Single user now, multi-user-ready authentication

- Status: Accepted
- Date: 2026-11-07

## Context

The server is typically hosted on a LAN or behind a TLS reverse proxy. It should
be as simple as possible to set up, and signing in from a phone should feel normal.
A future Switch app needs to authenticate without anyone typing a password on a Switch.

## Decision

- **Data model:** a single user, but every seed, preset, job and device record
  carries an `owner_id`. Shared game files are owned by the instance.
- **First run:**
  1. The container prints a one-time setup link to its logs, so no one else on the
     network can claim the server first.
  2. The wizard asks for a username and the public URL.
  3. The user chooses a passkey and/or a password.
- **Passkeys (WebAuthn):** need HTTPS (see ADR 0005). On plain HTTP the UI explains
  why it offers password sign-in only.
- **Password:** uses the right `autocomplete` attributes so password managers work.
  Hashed with Argon2id.
- **Sessions:** 90-day cookie that renews as you use it (`Secure`, `HttpOnly`, `SameSite=Lax`).
- **Protection:** login rate limiting and CSRF protection.
- **Switch app:**
  - The web UI shows a short pairing code (about 6 characters, 5-minute lifetime, QR optional).
  - The app exchanges it for a long-lived **device token**.
  - Only a hash of the token is stored.
  - Its scope is narrow (list seeds, download mods, generate from a preset).
  - It is named per device and can be revoked.
  - Pairing also records the Switch's name and IP, which the app refreshes each time it launches.
- **One interface:** all authentication goes through a single interface, so
  multi-user accounts can be added later without a redesign.

## Consequences

- Passkeys are tied to the configured domain. Changing the domain invalidates them,
  so a password or recovery codes must always remain available.
- Moving to multiple users means adding accounts, not migrating data.
